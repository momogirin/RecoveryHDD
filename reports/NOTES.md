# 복구 진행 기록

사람이 읽는 텍스트 기록만 둔다. 사진/영상/디스크 덤프/큰 스캔 원본은 저장소 밖(`~/Documents/recovered/`)에 있다.

## 대상
- 외장하드 5TB, 물리 디스크 disk4(재연결 후 disk5), APFS 파티션 s2 (오프셋 210,763,776)
- 식별자는 재연결할 때마다 바뀔 수 있다. 매번 `diskutil list external` 로 확인한다.

## 1. 컨테이너 슈퍼블록 (reports/01_inspect.txt)
- 블록 0 은 정상 NXSB, 체크섬 OK, 블록 4096B, 용량 5.00TB
- **xid = 1, next_xid = 2, 볼륨 목록(fs_oids) 비어 있음** → 새로 초기화된 컨테이너 상태
- 체크포인트 디스크립터 영역(블록 1..284) 중 2블록만 사용(CHECKPOINT_MAP, NXSB, 둘 다 xid 1)
- 암호화: flags=0, keylocker 없음. 컨테이너 수준 암호화 흔적 없음. NXSB 가 정상 읽히므로 Seagate 하드웨어 잠금도 아님
- **결론: 이 위치에는 옛 체크포인트가 없다.** (1순위 단순 경로 불가)
- 원인(초기화 경위)은 **미확인**

## 2. 앞 100GB NXSB/APSB 스캔
- 발견: NXSB 블록 0, 2 (모두 xid 1). APSB 없음.

## 3. 데이터 분포 샘플링 (reports/02_survey.txt, 128MB 간격)
- 0-250GB: 데이터 100%, JPEG 시작 20, MP4 ftyp 6
- 250-500GB: 데이터 48%, JPEG 7
- 500GB 이후: 전부 0 → **데이터는 앞 약 500GB 안에 있다**

## 4. 전체 스캔 중 연결 끊김
- 189.6GB 지점(22:12)에서 케이블이 빠짐(PC 위치 이동). 이후 전부 `Device not configured`
- 디스크 번호가 disk4 → disk5 로 바뀜. 슬립은 아니었음(caffeinate 정상, 로그에 슬립 없음)
- 0~189GB 구간 결과: NXSB 2개(블록 0, 2)만 발견, APSB 없음
- 코드 수정: 장치 끊김 감지 시 즉시 중단하고 이어서 돌릴 블록 번호 출력

## 5. 이어서 스캔 (블록 46,000,000 ~ 137,000,000, 약 184~557GB)
- 372.7GB 완전히 읽음, 읽기 오류 0, **NXSB/APSB 발견 0**
- 정리: 0~557GB 전체(데이터가 있는 구간)에서 유효한 옛 NXSB/APSB 없음 (새 컨테이너의 NXSB 2개뿐)
- 샘플링상 557GB 이후는 비어 있어 스캔하지 않음 (샘플링은 듬성듬성이라 완전 증명은 아님)
- **결론: 파일명/폴더 구조를 담은 옛 메타데이터는 디스크에서 찾지 못했다.** 1순위 경로 불가

## 다음
- 2순위: 앞 약 560GB 에서 JPEG/RAW/MP4 시그니처 기반 추출 (파일명 없이 번호+EXIF 날짜로 저장)
- 조각화 위험이 있으므로 결과를 검증한다. 마지막에 열림 검증 단계

## 6. 샘플 추출 (2026-11-20)
- 앞 20GB에서 JPEG 5장, `ftyp` 3개 추출. JPEG 5장 전체 디코딩 OK (2976x1984, Canon EOS R8, 촬영 2024-03-06)
- `ftyp crx ` 2개는 MP4가 아니라 **Canon CR3 RAW 사진**(6000x4000)이었음 → 브랜드별 확장자 판별 추가
- 영상 1개(404MB, 28.2초) 구조 정상
- 결론: 시그니처 복구는 실제로 작동한다. 파일명은 없음

## 7. P1 목록 만들기 구현 (2026-11-21)
- `catalog` / `summary` 명령 추가. 이어하기, 끊김 감지, 큰 영상 건너뛰기 지원
- 합성 이미지 단위 테스트 12개 통과 (`python3 -B -m unittest discover -s tests -t .`)
- 테스트로 찾은 버그 2건 수정: JPEG 끝(EOI)이 버퍼 끝에 있으면 오판 / 잘린 JPEG 뒤에 다른 JPEG가 이어지면 합쳐서 정상 판정
- 실제 복구 샘플 8개로 만든 이미지에서 길이 8/8 일치, 종류·촬영일·카메라 판별 정상
- 알려진 한계: EXIF 촬영 시각은 현지 시각, MP4 `mvhd` 시각은 UTC → 날짜별 폴더에서 영상은 하루 어긋날 수 있음(처리 방식 미정)
- 실제 하드 전체에 대한 catalog 실행은 아직 안 함

## 8. P2~P5 구현 (2026-11-21)
- 추가: `server`(로컬 웹 서버, 토큰·Host/Origin 검사), `extract`(계획·묶음 추출·이어하기), `verify`(구조/디코딩 검증), `devices`, `guards`(저장 경로·용량 가드), `ownership`(sudo 시 홈/소유자), `ui/index.html`
- 실행: `sudo python3 -B -m apfsrecover gui` → 출력된 주소를 브라우저에서 연다
- 테스트 30개 통과. 헤드리스 Chrome으로 UI를 끝까지 조작해 확인(검사→결과→계획→묶음 복구→검증→보고서). 꺼낸 8개 파일은 원본 샘플과 바이트까지 동일, 검증 8/8 통과(사진 5개 디코딩, 나머지 구조 확인)
- 수정한 버그: 1GB 미만 묶음 크기가 1GB로 처리됨 / 재검사 시 옛 목록에 이어 붙고 번호가 섞임(→ archive 보관)
- **아직 하지 않은 것**: 실제 하드(5TB)에 대한 GUI 검사·복구, sudo 상태에서의 `~` 해석과 파일 소유자 변경(코드는 있으나 실측 전), 윈도우, 영상 재생 확인(ffprobe 없음), RAW 현상 프로그램 열림 확인

## 9. 자동 모드 · 맥 실행 파일 (2026-11-21)
- 간편 복구: 디스크 + 저장 폴더 + 종류만 정하고 [자동 복구 시작] → 검사 → 복구 → 검증이 한 작업으로 이어짐. 저장 공간이 모자라면 복구 전에 멈추고(`needs_plan`) 계획 화면으로 넘김(검사 결과는 보존)
- `launch/mac/RecoveryTool.command`: 더블클릭 → macOS 비밀번호 창 → 브라우저. 관리자 창만 뺀 사본으로 동작 확인. **비밀번호 창 자체는 미확인**
- 화면의 [도구 종료] 버튼(작업 중에는 거부)
- 테스트 34개 통과. 헤드리스 Chrome으로 자동 모드·단계별 모드 모두 끝까지 확인
- 점검 중 찾은 버그: 화면 전환이 HTML 순서로 되어 있어 새 화면을 끼워 넣자 전부 한 칸씩 밀림 → id 기준으로 수정. 텍스트만 읽는 점검으로는 놓쳤고 스크린샷으로 발견
- 배포 계획: design/04-distribution.md (맥용·윈도우용 따로. 윈도우는 미구현)
