# 06. 맥북 작업 계획서

> 이 문서는 **맥북에서 이어서 작업하는 Claude 세션**이 읽고 바로 일할 수 있게 쓴 것입니다.
> 기준: `main` 브랜치 `da11c00` (윈도우에서 만든 것까지 반영). 사용자는 비개발자이며 **짧은 한국어, 결론 먼저, 추측 금지, 확인한 것/못 한 것 구분**을 원합니다.

## 0. 지켜야 할 규칙
- 복구 대상 **원본 디스크는 읽기만** 합니다. 쓰기·포맷·마운트 변경 금지. 실제 디스크를 열어 보는 시험은 사용자가 시킬 때만 하고, 평소에는 가짜 이미지(`tests/synth.py`)로 시험합니다.
- 빌드(.app, .exe)는 **매번 새 이름**으로 만듭니다(예: `RecoveryHDD_mac_v1`). 기존 산출물을 덮어쓰지 않습니다.
- 커밋·push는 사용자가 시킬 때만 합니다. 작업은 새 브랜치에서 하고, main에는 사용자가 합치라고 할 때 합칩니다.
- 화면 글자는 한국어. 화면이 움직이면 안 됩니다(`design/02-ui-spec.md`의 레이아웃 안정성 규칙 9개).

## 1. 프로젝트 요약
- 디스크 복구 프로그램 `RecoveryHDD`. 구조가 손상된 APFS 디스크에서 파일을 직접 찾아(카빙) 꺼냅니다. 엔진은 `apfsrecover/`(파이썬), 화면은 `apfsrecover/ui/index.html`(로컬 웹 UI), 윈도우용은 pywebview exe.
- 흐름: 검사(`catalog.py`) → 꺼내기(`extract.py`) → 열림 확인(`verify.py`, ZIP 복원은 `zipfix.py`) → 결과.
- 실행: `python3 -m apfsrecover gui` (관리자 권한 필요, 브라우저로 열림). 시험: `python3 -m unittest discover -s tests` (모두 통과해야 함).
- 사용자 디스크: 5TB APFS. 지금까지 약 371.8GB 구간만 검사했고 파일 17,230개를 찾았습니다.

## 2. 해야 할 일 (우선순위 순)

### 2-1. 맥에서 소스가 도는지 확인 (먼저)
윈도우에서만 만들고 시험해서, 맥에서는 **한 번도 실행해 본 적이 없습니다.** 코드를 읽어 보면 맥 처리가 들어 있는 곳은 `devices.py`(diskutil), `power.py`, `fsbrowse.py`, `server.py`의 폴더 열기입니다.
- 단위 시험 전체 실행 → 실패 항목 정리.
- `python3 -m apfsrecover gui --port N` 으로 띄워서 브라우저로 화면 확인(디스크 목록, 폴더 선택, 가짜 이미지 검사~꺼내기~열림 확인 한 바퀴).
- 확인할 것: 폴더 선택창(`nativepick.py`는 tkinter 사용 — 맥 파이썬에 tkinter가 없으면 대체 방법 필요), 관리자 권한 안내(`privilege.py`), 전체 디스크 접근 권한 안내, 절전 방지(`privilege.py`/`power.py`는 윈도우 위주 → 맥은 `caffeinate`로 대체 필요할 수 있음).
- 결과를 **됨/안 됨/못 해 봄**으로 표로 보고.

> **2026-11-25 윈도우에서 진행한 것:** 2-2, 2-3 은 구현 완료(`apfsrecover/tailcheck.py`, `App.format_check`, [도구] 화면, 시험 `tests/test_tailcheck.py`·`tests/test_formatcheck.py`, 빌드 `dist/v8/RecoveryHDD_v8.exe`).
> 2-4 는 이미 있던 기능이었음(`guards.check_dest` 가 원본 디스크의 모든 파티션 경로를 거부, `tests/test_windows.py` 에 시험 있음).
> 맥에서는 2-1(맥 실행 확인) → 2-5(미리보기) 순서로 하면 됩니다. 2-2·2-3 은 맥에서도 [도구] 화면이 도는지만 확인하세요.
> 포맷 점검은 '이전 검사 결과 재사용'으로 이어진 옛 세션(known_from.json)에서 꺼낸 파일도 디스크 위치(offset)로 맞춰 함께 셉니다.

### 2-2. 끝부분 촘촘 검사 (새 기능) — 완료
- 배경: 기본 검사 범위는 128MB마다 4KB를 찍어 보고 "내용이 있는 마지막 위치 + 샘플 간격 + 2GB"까지만 읽습니다(`server.py`의 `_scan`, `survey.py`). 그래서 5TB 중 7.4%만 읽었고, 뒤쪽에 작은 파일이 따로 있으면 놓칠 수 있습니다.
- 할 일: 검사 끝 이후 구간을 더 촘촘한 간격(예: 32MB)으로 찍어 보는 옵션을 추가하고, 결과를 "뒤쪽에 데이터 있음/없음"으로 화면에 보여 줍니다. 5TB 기준 약 20분 예상(추정, 실측 아님).
- 이어하기·취소, 이미 찾은 구간 재사용(`known`)과 맞물려야 합니다.
- 시험: 가짜 이미지 뒤쪽에 작은 파일을 심어 두고, 기본 검사는 놓치고 촘촘 검사는 찾는 것을 확인.

### 2-3. 포맷 전 점검 화면 (새 기능) — 완료
사용자가 "다 꺼낸 뒤 포맷해서 쓰고 싶다"고 했습니다. 프로그램 안에서 알려 줄 것:
- 꺼낸 파일의 저장 위치가 **복구 대상 디스크와 다른 물리 디스크**인지.
- 열림 확인이 끝났는지, 실패·복원본 개수.
- 검사하지 않은 구간이 얼마인지(추정이라는 점 명시).
- 결과: "포맷해도 됩니다 / 확인할 게 있습니다" + 이유 목록. 프로그램은 포맷 기능을 넣지 않습니다(읽기 전용 원칙).

### 2-4. 원본과 같은 디스크로 저장하는 것 막기 — 이미 있음
꺼낼 위치를 고를 때 복구 대상 디스크와 같은 디스크면 경고(`guards.py`의 `check_dest` 확장). 맥은 `diskutil info`로 디스크 판별.

### 2-5. 결과 탐색 미리보기
꺼낸 사진·영상 썸네일(`server.py`에 `_thumbs` 캐시가 이미 있음. 어디까지 구현됐는지 먼저 확인할 것).

## 3. 나중에 (사용자 결정 필요)
- 디스크 이미지 백업: 5TB 전체는 공간이 없어 어렵다는 것이 사용자 판단. "앞쪽 약 400GB만"은 2-2 결과를 본 뒤 다시 의논.
- 디스크 건강 점검(SMART), 중복 정리, 조각난 파일 이어 붙이기, 암호·lzma·zstd ZIP 확인.
- 맥 `.app` 빌드(py2app 또는 PyInstaller): 2-1이 끝난 뒤.

## 4. 알려진 한계 (이미 사용자에게 말한 것)
- ZIP 복원본: 마지막 항목이 잘린 ZIP은 그 항목을 되살릴 수 없음. 암호·lzma·zstd 항목은 CRC 확인 불가(확인 못 함으로 셈).
- 새 파일 형식(PDF, HWP, PNG, WebP, AVI 등)은 가짜 파일로만 시험함. 실제 샘플 확인 필요.
- 윈도우 exe(`dist/v7/RecoveryHDD_v7.exe`)는 개발자가 직접 실행해 보지 못함(관리자 권한).
