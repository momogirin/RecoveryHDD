# 02. UI 명세

> **현재 화면은 v2 입니다** (시안: [mockup/ui-v2.html](mockup/ui-v2.html), 구현: `apfsrecover/ui/index.html`).
> 아래 "화면 1~6"은 v1(6단계 탭) 설계이며 기록으로 남긴다.
>
> ## v2: 3단계 (디스크 → 복구 설정 → 진행·결과)
> | 화면 | 내용 |
> |---|---|
> | 디스크 | 이름·연결·형식·용량 카드. 읽기 전용 안내는 제목줄 배지와 이 화면의 안내 한 줄뿐 |
> | (검사) | 디스크를 훑는 진행 화면. 시안에는 없던 화면이며 같은 디자인(링·통계)을 쓴다. 이미 검사한 같은 디스크면 건너뛴다 |
> | 복구 설정 | 사진·RAW·영상 카드(개수·용량), 저장 폴더, `_의심` 토글, 한 문장 요약, [고급 설정: 나눠서 꺼내기·다시 검사·전체 검사] |
> | 진행 | 링, 꺼낸 파일·용량·남은 시간, 종류별 개수, 방금 꺼낸 파일 썸네일. 이어서 [열림 확인] 단계 |
> | 결과 | 개수·열림 확인 요약, 썸네일 격자, [폴더 열기], 문제 파일·검증 방법은 접어 둠, [보고서 저장] |
>
> 시안과 달라진 점(구현하며 필요해서 바꾼 것): ① 검사 진행 화면 추가 ② APFS 가 아닌 디스크도 선택 가능(경고 칩만 표시. 윈도우에서 포맷된 디스크도 서명 복구가 되기 때문)
> ③ 결과 문구 "모두 열리는 것을 확인" → "모두 정상으로 확인"(영상은 구조 확인까지만 하므로) ④ 결과에 "자세히"(검증 방법)를 항상 표시 ⑤ 고급 설정 추가 ⑥ 제목줄에 [종료] 버튼
> ⑦ 전용 창에서는 화면 위쪽의 이름을 숨김(윈도우 제목줄이 이미 보여 줌)

# (이전 설계) v1 UI 명세

시안: [mockup/index.html](mockup/index.html)

## 공통
- 상단에 항상 **"읽기 전용: 원본 디스크에는 아무것도 쓰지 않습니다"** 표시
- 진행 단계 표시줄: ① 디스크 ② 검사 ③ 결과 ④ 계획 ⑤ 복구 ⑥ 검증
- 판정 라벨은 3종류만 쓴다: `확인됨`, `의심`, `불명`. 색만으로 구분하지 않고 글자와 아이콘을 같이 쓴다
- 오래 걸리는 작업은 항상 **진행률, 처리 속도, 남은 시간 추정, 취소 버튼**을 보여 준다
- 오류 문구는 "무슨 일이 일어났나 → 데이터는 안전한가 → 다음에 할 일" 순서로 쓴다
  - 예: "하드와 연결이 끊겼습니다. 원본은 읽기만 했으므로 안전합니다. 케이블을 다시 꽂고 [다시 연결]을 누르세요."

## 화면 1. 디스크 선택
- **외장 디스크 목록**을 보여 준다(이름, 용량, 연결 방식, 식별자). 내장/시스템 디스크는 목록에 올리지 않는다
- 선택한 디스크 요약: 파티션, 파일시스템 인식 결과(예: "APFS, 마운트되지 않음")
- 버튼: `[검사 시작]`
- 상태: 디스크 없음 → "연결 후 [새로고침]". 권한 부족 → 관리자 권한으로 다시 실행하는 방법 안내

## 화면 2. 검사 진행
- 단계 표시: 구조 확인 → 데이터 분포 → 파일 찾기
- 진행률 막대, 읽은 GB / 전체 GB, MB/s, 남은 시간, 지금까지 찾은 파일 수
- `[취소]`(디스크에는 영향 없음 안내), 케이블이 빠지면 자동 중지 + `[다시 연결]`
- 예상 시간이 길면(예: 1시간 이상) 시작 전에 알려 준다

## 화면 3. 검사 결과
- **한 줄 결론**: 예) "사진·영상 N개(약 X GB)를 찾았습니다. 원래 파일명은 복구할 수 없습니다."
- 종류별 표: 개수, 용량, 구조 점검 결과(확인됨/의심)
- 촬영일 분포(월별 막대), 카메라 모델 목록
- 디스크 상태 요약: 새로 초기화된 컨테이너인지, 암호화 흔적, 데이터가 있는 구간
- 모르는 것 목록: "삭제된 옛 파일이 섞여 있을 수 있음(구분 불가)" 등 알려진 한계
- 버튼: `[복구 계획 세우기]`, `[결과 저장]`

## 화면 4. 복구 계획
- **무엇을**: 종류 체크(JPEG, RAW, 영상), 촬영일 범위, `의심` 포함 여부
- **얼마씩**: 한 묶음 크기를 "개수" 또는 "GB"로 입력. 묶음이 몇 개로 나뉘는지 즉시 계산해서 표시
- **어디에**: 저장 폴더 입력/선택 → 즉시 검사
  - 여유 공간, 이번 묶음 필요량, 마진 → `충분함 / 부족함`
  - 거부: 원본 디스크 안, 저장소 폴더 안, 시스템 폴더
- 폴더 구조 미리보기(날짜별 예시 3줄)
- 버튼: `[이 묶음 복구 시작]`(비활성 조건을 이유와 함께 표시)

## 화면 5. 복구 진행
- 묶음 번호(예: 2/7), 파일 N/M, GB, 속도, 남은 시간
- 최근 꺼낸 파일 목록(이름, 크기, 상태)
- `[일시정지]`, `[중단]`. 중단/끊김 시 이어서 할 위치를 저장하고 안내
- 묶음이 끝나면 요약 + `[다음 묶음]` `[검증으로]`. 폴더를 비워도 이어갈 수 있음을 안내

## 화면 6. 검증 결과
- 파일 수: 열림 확인 N / 실패 M / 미검사 K
- 실패 목록(이유: 잘림, 구조 오류, 헤더 불일치)과 `[실패 파일 폴더 열기]`
- 영상은 "구조 확인까지만 했고 재생 확인은 하지 못했다" 같이 **검증 범위**를 명시
- `[보고서 저장]`(텍스트, 개인정보 가림)

## 접근성·기타
- 키보드만으로 모든 버튼에 접근 가능, 상태는 글자로도 표시
- 라이트/다크 둘 다 지원
- 모바일 폭은 지원 대상이 아니지만 좁은 창에서도 깨지지 않게 한다
- 영어 번역은 문구를 한곳에 모아 두어(`i18n`) 나중에 추가한다

## 변경 기록: 진행 화면 v3 (2026-11-24, 브랜치 `ui-v3-progress`)
시안: `design/mockup/ui-v3-progress.html`. 구현: `apfsrecover/ui/index.html`만 수정(서버·엔진 변경 없음).
- 검사·꺼내기·열림 확인 화면은 위쪽 3단계 대신 **단계 길**(사진 찾기 → 꺼내기 → 열림 확인)을 쓴다. 끝난 단계는 걸린 시간을 보여 준다(이번 실행 중 끝난 단계만. 이전 기록은 "완료"만).
- **항상 보이는 안심 줄**: 원본 디스크는 읽기만 해요 / 잠자기 방지 켜짐 / 저장 위치. 프로그램과 연결이 끊기면 "잠자기 방지"는 숨긴다(확인할 수 없으므로).
- 큰 제목 줄에 **남은 시간 + 끝나는 시각**. 시작 후 90초 전이거나 서버가 남은 시간을 못 주면 "계산하고 있어요". 15분 넘게 남으면 시각을 5분 단위로 맞춘다. 열림 확인은 서버가 남은 시간을 주지 않아 화면이 경과 시간과 진행률로 추정한다.
- 종류별 숫자는 작은 막대로 표시(종류가 늘어도 자동으로 줄바꿈).
- 상태별 화면: 일시 중지 / 중단 / 연결 끊김 / 다시 연결됨 / 디스크 불안정 / 저장 공간 부족 / 시작 거부. 카드 순서는 "무슨 일 → 원본은 안전 → 할 일". 오류 문구는 엔진이 준 문장을 그대로 쓴다.
- 연결 끊김 후 같은 디스크가 다시 꽂히면 [이어서 하기]가 **하나만** 켜진다(이전에는 비활성 버튼과 별도 알림에 버튼이 2개).
- 프로그램과 화면의 연결이 끊기면 숫자를 회색으로 바꾸고 "마지막 업데이트 N초 전"을 보여 주며 버튼을 잠근다.
- 아래 버튼 줄은 창 아래에 고정(최소 창 900×640에서도 보임).
- 열림 확인 화면의 버튼은 [확인 건너뛰기] 하나(이전: 일시 중지·중단).
- 아직 안 한 것: 열림 확인 중 미리보기 줄, 이모지→선 아이콘 전체 교체, 125·150% 배율 확인, 실제 exe 창 확인.

## 변경 기록: 기록·보고서 버전 호환 (2026-11-24)
코드: `apfsrecover/compat.py`(새), `jsonl.py`, `catalog.py`, `extract.py`, `verify.py`, `server.py`. 테스트: `tests/test_compat.py`.
- 세션 폴더에 `session_meta.json`(형식 번호, 현재 2)을 남긴다. 번호가 없는 기록은 "이전 버전(1)"으로 읽는다. 이전 기록을 이어 쓰면 `upgraded_from: 1`로 표시한다.
- 읽을 때 빠진 값은 기본값으로 채우고, 모르는 종류·추가 항목은 버리지 않고 보존한다. 쓸 수 없는 줄은 건너뛰되 개수를 센다(보고서와 화면 알림에 표시).
- 더 새 버전이 만든 기록은 읽기만 하고 번호를 낮추지 않는다. 화면에서 "이어서 하기는 하지 마세요"를 알린다.
- 이 화면이 모르는 종류의 파일이 검사 기록에 있으면 "N개 있어요, 꺼내지 않고 그대로 둡니다"를 알린다(조용히 빠지지 않게).
- 보고서 맨 위에 `[형식] 보고서 v2 · 기록 v1 (이전 버전 기록을 읽음)` 줄을 넣는다. 사람이든 프로그램이든 어느 버전 보고서인지 알 수 있다.
- 알려진 한계: 이전 버전의 필드 이름이 바뀐 적이 있는지는 확인하지 못했다(지금까지 1개 버전만 있었다). 그런 변화가 생기면 `compat.py`의 정리 함수에 이름 대응을 추가한다.

## 변경 기록: 파일 형식 확장 1차 (2026-11-24)
코드: `apfsrecover/formats_more.py`(새), `catalog.py`, `extract.py`, `verify.py`, `formats.py`, `ui/index.html`. 테스트: `tests/test_formats_more.py`.
- 새로 찾는 형식: PDF, 한글 HWP(5.x)·옛 오피스(doc/xls/ppt, OLE 구조), 한글 HWPX(ZIP 안 `Contents/` 로 구분), PNG, GIF, WebP, BMP, AVI, WAV, RTF, 7z, SQLite. txt 는 파일을 알아볼 표식이 없어 넣지 않았다.
- 검사 속도: 이전에는 시그니처 3개를 버퍼 전체에서 찾았다. 이제 4096 바이트 블록의 시작 16바이트만 보고 종류를 가린다(종류가 늘어도 한 번만 훑는다). 기존 JPEG/BMFF/ZIP 판별 결과는 같다(기존 테스트 통과).
- 길이 판정: PDF(끝 표시 + 증분 저장/내장 PDF 구분, 선형화 PDF는 머리의 길이), OLE(FAT 로 사용 구역 수 계산), PNG/GIF(조각을 끝까지 따라감), RIFF(머리의 길이), BMP(머리 + 그림 크기 일치), RTF(괄호 짝), 7z(머리 CRC + 끝 머리 CRC), SQLite(쪽 수 × 쪽 크기). 길이를 확정할 수 없으면 기록하지 않는다.
- 최소 크기(작은 조각·아이콘이 결과를 어지럽히지 않게): PNG 20KB, GIF 5KB, WebP 10KB, BMP 50KB, WAV·AVI 100KB, SQLite 8KB 등.
- 열림 확인: 같은 판별 코드를 꺼낸 파일에 다시 돌려 길이·구조가 맞는지 보고(structure), 이미지는 Pillow 로 실제 열어 보고(decode), SQLite 는 `quick_check` 로 확인한다. PDF·한글·오피스·7z·RIFF·RTF는 구조 확인까지만(열림은 확인하지 않음).
- 정리 폴더: `사진`(PNG·GIF·WebP·BMP 포함), `영상`(AVI 포함), `문서`(PDF·한글·오피스·RTF·docx 등), `압축`(zip·7z), `음성·데이터`(WAV·SQLite, 화면에서 기본은 꺼짐).
- 날짜: 새 형식은 촬영일 정보를 읽지 않아 `날짜불명` 폴더로 들어간다.
- 실제 파일로 확인(이 PC의 파일, 읽기만): 7z 20/20, PDF 8/8, GIF 40/40, WAV 40/40, SQLite 37/40(나머지는 SQLite 아님·암호화), BMP 35/35(열 수 있는 것), doc·xls·ppt 대부분 정확. WebP·AVI 는 이 PC 에 실제 샘플이 없어 가짜 파일 테스트로만 확인했다.
- 알려진 한계: 조각나 저장된 파일은 일부만 찾거나 못 찾을 수 있다. 암호가 걸린 PDF·ZIP 은 구조만 확인된다. SQLite 는 머리의 쪽 수가 실제 파일보다 작은 경우(쓰기 중 중단 등) 짧게 잡힐 수 있다.

## 변경 기록: 이전 검사 결과 재사용 (2026-11-24)
코드: `catalog.py`(known), `server.py`(reusable, /api/sessions/reusable, scan/start 의 reuse), `ui/index.html`. 테스트: `tests/test_reuse.py`.
- 새 검사를 시작할 때 같은 디스크(지문과 크기가 같고 끝까지 검사된 기록)의 이전 세션이 같은 위치의 `session*` 폴더에 있으면 "이전 검사 결과를 활용할까요?"를 묻는다.
- [이전 결과 활용]이면 이전 검사에서 찾은 파일 구간은 디스크에서 다시 읽지 않고 건너뛰며, 지나갈 때 항목을 새 검사 기록에 옮겨 적는다(`reused: true` 표시). 나머지 구간에서 새 종류를 찾는다. [아니요]면 처음부터 모두 읽는다.
- 끊겼다 이어할 때도 같은 이전 기록을 다시 쓴다(`known_from.json`). 결과는 중간에 멈췄다 이어해도 처음부터 한 번에 돌린 것과 같다(테스트).
- 읽는 양: 가짜 디스크 시험에서 처음부터 읽을 때의 40% 미만. 실제 효과는 이전 검사에서 찾은 파일이 디스크의 얼마를 차지하느냐에 달렸다.
- 한계: 이전에 찾은 파일 안쪽은 다시 보지 않으므로, 그 안에 숨은 새 종류는 찾지 못한다. 디스크 내용이 이전 검사 뒤에 바뀌었다면(원본은 읽기 전용이라 보통 없다) 맞지 않을 수 있다 — 같은 디스크 확인은 앞 64KB와 크기만 본다.
- 문구: 검사 화면의 "사진 찾기/사진과 영상을 찾고 있어요"를 "파일 찾기/파일을 찾고 있어요"로 바꿨다(모든 종류를 한 번에 찾으므로).

## 변경 기록: ZIP 복원본 (2026-11-24)
코드: `apfsrecover/zipfix.py`(새), `verify.py`, `compat.py`, `server.py`, `ui/index.html`. 테스트: `tests/test_zipfix.py`.
- 배경: 실제 디스크에서 ZIP 7개를 찾았고 5개가 "의심"이었다. 꺼낸 파일을 분석하니 항목은 대부분 온전한데 목차(중앙 디렉터리)가 없거나 마지막 항목이 잘려, 윈도우·파이썬이 "zip 파일이 아님"이라고 했다.
- 열림 확인에서 ZIP 계열(zip·docx·xlsx·pptx·hwpx)이 실패하면 온전한 항목만 모아 새 ZIP 을 `저장폴더\_복원본\<원래 경로>` 에 만든다. 원본은 그대로 둔다. 상태는 `fixed`(요약의 `fixed` 개수), 항목 수·잘린 항목 여부는 `salvage` 항목에 기록한다.
- 항목마다 압축을 풀어 CRC32 로 확인한 것만 넣는다(저장·deflate·bzip2). 그 밖의 방식은 크기만 믿고 '확인 못 한 항목'으로 센다. 처음 문제가 생긴 곳에서 멈춘다. 데이터 설명자(스트리밍) ZIP 과 4GB 넘는 ZIP64 목차도 쓴다.
- 실제 데이터 확인(꺼내 둔 의심 ZIP 5개, 임시 폴더에 복원 후 삭제): 6/30/27/2/57개 항목 복원, 전부 열리고 모든 항목 CRC 정상. 3개는 마지막 항목 하나가 잘려서 빠졌다.
- 결과 화면: "ZIP N개는 복원본으로 열 수 있어요", 자세히에 복원본 경로·항목 수. [열림 다시 확인] 버튼을 추가해 이미 꺼낸 세션에서도 복원본을 만들 수 있다.
- 한계: 잘린 항목은 그 앞부분까지도 쓰지 않는다. 조각난 ZIP 의 뒷부분이 디스크 어딘가에 있어도 잇지 않는다(어디인지 알 수 없다). 암호 ZIP 은 CRC 를 확인할 수 없는 항목이 생긴다.
